\section{Introduction and Motivation}

\subsection{The IVI Thermal Landscape}

Modern automotive in-vehicle infotainment (IVI) head units increasingly host high-thermal-design-power SoCs --- Qualcomm SA8255P, SA8295P, and SA8775P; Samsung Exynos Auto V920; and emerging RISC-V automotive parts --- alongside class-D amplifiers, terrestrial and satellite tuners, and the head unit's own board-temperature sensors. These designs operate across automotive ambient ranges that span roughly $-40$ to $+85\,^\circ\mathrm{C}$, often inside enclosures with limited passive airflow and minimal natural convection when the vehicle is stationary. Fan-based active cooling, once a desktop concern, has become a near-default response to the resulting thermal envelope.

The control problem is not only to map temperature to fan duty. A portable thermal controller must preserve the same safety ordering, timing semantics, and configuration meaning across a Linux daemon, an RTOS firmware, and a constrained MCU target, even though those platforms source sensors, context signals, tachometer readings, and actuator drivers through different mechanisms. This paper focuses on that separable control core.

\subsection{Context-Aware Policy as an Optional Layer}

The core observation behind \texttt{thermal-core} is that the closed-loop governor should stay generic while policy can depend on non-temperature context. Vehicle speed, ignition state, drive mode, HVAC state, service mode, or workload can legitimately shape where a thermal controller chooses to spend margin. The core therefore treats these signals as typed context inputs and routes them through configured \emph{modifiers}: deterministic curves that can shift trip points or PID setpoints before governor evaluation, and cap actuator output after governor evaluation.

The reference modifier in this paper is acoustic-aware fan control. Inside a quiet cabin, a fan that disappears at 80\,km/h of road and tire noise can be conspicuous at a red light; the same silicon temperature may therefore justify a different fan response at standstill than at highway speed. That application is treated as a worked example in Section~\ref{sec:reference-policy}, not as a special case inside the governor.

\subsection{Project Boundary}

\texttt{thermal-core} is deliberately a small library, not a monolithic daemon. The core owns:

\begin{itemize}[leftmargin=*]
    \item zone state, sensor aggregation, trip evaluation, governors (step-wise and PID), policy modifiers, arbitration across zones, fault detection, and numeric telemetry;
    \item deterministic stepping over typed input snapshots and output actuator frames, with no syscalls, no heap allocation after init, and Q16.16 fixed-point arithmetic that is identical bit-for-bit across all supported targets;
    \item fixed-size configuration structures populated from JSON on Linux or from generated static-const C on an MCU.
\end{itemize}

The platform layer outside the core owns blocking I/O, configuration loading, transport framing, and target-specific peripheral drivers. The reference Linux daemon binds \texttt{thermal-core} to \texttt{hwmon}, SocketCAN, and UDP telemetry; the reference ESP-IDF firmware binds it to LEDC pulse-width modulation, PCNT tachometer input, TWAI controller-area-network, and 1-Wire temperature probes. Wire framing for telemetry and runtime tuning lives in a separate \texttt{protocol/} module so the policy library can be embedded by callers that have no use for the binary frame format.

Domain-specific context --- vehicle speed sourced from OBD-II via CAN, in the reference design --- enters the core only as a typed numeric signal in the input snapshot. The core never parses CAN frames, knows OBD-II request identifiers, opens sysfs files, allocates JSON objects, blocks on hardware, or depends on any vehicle-specific protocol. This is what ``protocol-agnostic'' means here: not that the project lacks a wire format, but that the thermal-control library at the centre of the project does not contain one.

\subsection{Contributions}

This paper documents four contributions, demonstrated by a reproducible reference implementation:

\begin{enumerate}[leftmargin=*]
    \item \textbf{An architectural separation} between deterministic thermal policy and platform I/O that lets one body of C99 logic run unmodified on a Linux development host, on an ESP32-C3 MCU under FreeRTOS, and (by structural readiness) on Renesas RH850-F1KM. The discipline that enables portability --- static allocation, fixed-point math, numeric event logging, snapshot-driven inputs --- is imposed up front rather than retrofitted.
    \item \textbf{A generic context-input and policy-modifier mechanism}: typed context signals shape pre-governor trip/setpoint offsets and post-governor actuator limits through configured curves, demonstrated with an acoustic-aware reference policy in Section~\ref{sec:reference-policy}.
    \item \textbf{A reproducible bench rig and scenario harness.} The plotted scenario benchmarks in this paper are regenerated from the deterministic plant model and control law by a single \texttt{make} target. Every plot cites a manifest entry --- the scenario telemetry CSV's SHA-256, the config-file SHA-256, the source git SHA, and the tool versions --- so a reviewer can trace any number on any plot back to the exact input that produced it. The formal hardware benchmark sweep, when captured on the bench rig, will extend the same manifest discipline to instrumented data.
    \item \textbf{An honest assessment} of what the architecture does not solve --- ISO 26262 readiness, AUTOSAR integration, calibrated sound-pressure-level measurement, multi-fan acoustic cancellation --- so that practitioners can pick up the parts that apply to their context without inheriting overclaims.
\end{enumerate}

\subsection{Outline of This Paper}

Part~I (\emph{Fundamentals of Portable Closed-Loop Thermal Control}) introduces related work, operating environments, the closed-loop control model, zones and sensors, deterministic curves, and timing semantics. Part~II (\emph{thermal-core Implementation}) covers the core boundary, component layout, per-tick implementation pipeline, configuration schema, control and telemetry interfaces, the acoustic-aware reference policy, deployment notes, and preliminary evaluation. Appendices catalogue the full reference configuration, the OBD-II frame reference used for vehicle-speed sourcing, the bill of materials for the reproducible bench rig, and the build-command reference.
