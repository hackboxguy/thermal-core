\section{Curves and Policy Functions}

\subsection{Curve Types}

\texttt{thermal-core} uses curves for command shaping, trip or setpoint offsets, fan-health baselines, and context policy modifiers. Curves are represented as fixed-size point tables with deterministic interpolation so the same configuration can be used on Linux and MCU targets.

\subsection{Generic Examples}

The simplest curve-like mapping is the actuator \texttt{state\_pwm[]} table: a step-wise zone produces a cooling-state index and each actuator maps that index to its own drive level. The fan-health detector uses a different curve shape, an eight-point PWM-to-RPM baseline, to compare measured tachometer speed against the expected value for a known-good fan. The acoustic-aware speed-to-cap curve is a reference-policy application, described later in Section~\ref{sec:reference-policy}.

\subsection{Implementation Notes}

Curves are fixed-size point tables evaluated by deterministic linear interpolation between adjacent breakpoints, with flat (clamped) extrapolation outside the table. Inputs, outputs, and the interpolation arithmetic are integer or Q16.16 fixed-point, so a curve evaluates bit-for-bit identically on the Linux host and the ESP32-C3. Breakpoints are validated at configuration load to be strictly ascending on the x-axis.

Configuration validation rejects duplicate or descending x-axis points. Modifier curves get additional value-range checks: PWM caps must be either zero or within actuator bounds, and trip/setpoint offsets are checked at every curve point so adjusted trips remain ordered and PID setpoints remain inside their configured ranges. The figure-regeneration pipeline renders the closed-loop scenario plots in Section~\ref{sec:eval-scenarios}; policy-specific before/after acoustic plots are deferred with the calibrated acoustic benchmark.
