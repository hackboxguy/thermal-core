\section{Control-Loop Implementation}

\subsection{Per-Tick Order}

The control model in Section~\ref{sec:control-model} is implemented as one single-threaded call to \texttt{thermal\_core\_step}. The platform supplies a snapshot of sensor, tachometer, and context samples; the core advances every module in a fixed order and writes one actuator output frame. The order below matches PRD §4.6 and the implementation in \texttt{core/thermal\_core.c}.

\begin{lstlisting}[language=C,caption={Per-tick control-loop order in \texttt{thermal\_core\_step}}]
thermal_core_step(ctx, snapshot, &out):
  // Step 3:  apply IIR filters per sensor; update zone-filtered temps
  // Step 4:  apply IIR filters per context; track ms-since-last-valid
  // Step 5:  evaluate policy modifier; cache pwm_cap + trip_offset_mc
  // Step 6:  for each zone:
  //            aggregate sensors (max / avg / weighted)
  //            run governor with offset-shifted trips and setpoint
  // Step 7:  for each actuator:
  //            max-wins arbitration across zones referencing it
  // Step 8:  apply post-governor modifier pwm_cap per actuator
  //            (skipped when driving zone is CRITICAL+)
  // Step 9:  step each fault detector; derive safety_override_up;
  //            apply force_pwm_max / shutdown actions; emit fault,
  //            fallback, safety, and shutdown events on edges
  // Post-v1: advisory fan-health update -- compare tach against the
  //            previous applied duty, skip non-steady / fault-
  //            overridden windows; telemetry only
  // Step 10: actuator dwell, spin-up boost, slew, and final clamp
  // Step 11: emit telemetry signals on configured cadence
\end{lstlisting}

Figure~\ref{fig:tick-pipeline} expands the same order into the module pipeline. The fault detectors may overwrite post-modifier duty upward, the fan-health detector taps state without commanding anything, and the actuator policy stage applies dwell, spin-up, slew, and final clamping before the frame leaves the core.

\subsection{Runtime Shadows}

Runtime tuning never mutates the immutable \texttt{thermal\_config\_t} passed to \texttt{thermal\_core\_init}. The core copies tunable trip points, PID gains, setpoints, and modifier curves into an internal shadow. \texttt{thermal\_core\_step} reads the shadow values, while command handlers validate prospective edits against the same safety invariants used at load time. In particular, runtime edits cannot make trip points descend, move PID setpoints outside configured bounds, or create modifier offsets that would make the shifted trip table invalid.

\subsection{Verification}

The control loop is verified at two levels. Per-module replay goldens cover curves, IIR filters, zone aggregation, the step-wise governor, the PID step, and each of the four fault detectors; every C golden is matched byte-for-byte by a Python reference under \texttt{test/reference/}. The full-loop golden \texttt{test/replay/golden/full\_step\_sweep.csv} drives \texttt{thermal\_core\_step} through a 600-tick scenario covering cold start, WARN under a modifier cap, anti-short-cycle dwell, spin-up from zero, CRITICAL dwell/slew bypass, a context ramp relaxing the cap, downward-slew recovery, runaway, and shutdown. Any commit that changes loop behavior produces a CI-visible diff against this canary.

Named safety-override unit cases live in \texttt{test/unit/test\_core\_step.c}: CRITICAL bypasses caps, SHUTDOWN bypasses caps and emits the shutdown event once, downward recovery obeys slew, upward safety override bypasses slew, dwell holds both on and off commands, CRITICAL turn-on bypasses active off-dwell, and spin-up disarms when demand drops to zero. The post-v1 fan-health detector carries its own replay golden --- \texttt{test/replay/golden/fan\_health\_drift.csv}, a four-phase degradation drift matched byte-for-byte by \texttt{test/reference/fan\_health.py} --- and unit cases that it never perturbs an actuator command frame.
