# Porting thermal-core

This guide is the short contract for bringing `thermal-core` to a new
MCU, RTOS, Linux/QNX service, or host-side integration. The portable
layers are `core/`, `protocol/`, and `support/`; platform drivers,
transports, file formats, and scheduler choices live outside them.

## Platform Contract

1. Provide monotonic time in milliseconds.
   `thermal_input_snapshot_t.now_ms` and command timestamps are
   unsigned 32-bit milliseconds. They must be monotonic non-decreasing
   and may wrap modulo `2^32`; the core uses wrap-safe unsigned
   differences, so the normal wrap at about 49.7 days is expected.

2. Build complete snapshots before each step.
   The platform owns sensors, tach reads, context sources, debounce,
   conversion timing, and stale-source detection. If a sample is absent,
   timed out, faulted, or otherwise untrustworthy, pass it with
   `valid = 0`. `sample_ts_ms` is the platform's timestamp for that
   sample in the same millisecond timebase as `now_ms`.

3. Keep callbacks non-blocking.
   `log_event` and `telemetry_emit` run synchronously from
   `thermal_core_step()` or `thermal_core_apply_command()`. Queue,
   coalesce, drop, or buffer records in the platform layer rather than
   blocking on disk, syslog, NVS/flash, UART drains, sockets, or locks.

4. Serialize access per context.
   A `thermal_core_t` is caller-owned and non-reentrant. Use one control
   thread/task per instance, or guard all API calls with a platform lock
   outside the core. Multiple independent `thermal_core_t` instances are
   fine because the portable layers have no mutable file-scope state.

5. Keep configuration immutable.
   `thermal_config_t` must be validated before init and remain alive and
   immutable for the lifetime of the context. Linux/QNX ports typically
   parse JSON into RAM at startup; MCU ports normally compile a
   `static const thermal_config_t` generated by `tools/json2static.py`.
   Runtime tuning commands update core shadow state within configured
   bounds; they do not mutate the config object.

## Small-Target Notes

The default `thermal_core_t` reservation is sized for the full v1 maxima.
Targets with around 2 KB of SRAM must use a constrained profile such as
`core/thermal_profile_tiny.h`, which reduces the context reservation to
1 KB and compiles optional features such as PID out when appropriate.

The portable layers are C99, fixed-size, and fixed-point. They use
`stdint.h` widths explicitly and are intended to remain clean on
compilers where plain `int` is 16 bits. They do not use floating point,
heap allocation, syscalls, platform clocks, or blocking I/O. `memcpy` and
`memset` are the sanctioned libc helpers for bounded storage and byte
encoding.

## Expected Port Shape

- A BSP or service loop samples platform inputs and fills
  `thermal_input_snapshot_t`.
- The loop calls `thermal_core_step()` at the configured control period.
- The platform applies each `thermal_output_frame_t` actuator command.
- A transport may link `protocol/thermal_wire.c` to carry telemetry and
  runtime commands; direct in-process API use does not need `protocol/`.
- `support/thermal_config_hash.c` is optional, but useful when comparing
  JSON-loaded and generated-static configs under the same feature profile.

## Minimum Validation

Before treating a port as usable, run the host gates first:

```sh
make test
make replay
make verify-portability
```

For constrained MCU work, also run:

```sh
make test-tiny-profile
```

Then add the target-specific build and size gate. For the CH32V003
reference port this is `make build-ch32`; other targets should provide an
equivalent cross-build that reports flash/SRAM and fails when the target
budget is exceeded.
